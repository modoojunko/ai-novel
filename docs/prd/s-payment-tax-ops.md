# S端 支付 · 税务对接纪要（发票 / 红冲 / 申报怎么落地）

> 2026-08-29 会话沉淀，依据《S端 扫码支付探索纪要》已拍板口径（决策 #8）。给运营者自己看：**税务这边到底要干什么、工作量多大、去哪操作**。只讲操作与口径，讲过的支付/退款机制不重复。
> 依据：[s-payment-explore.md](s-payment-explore.md) · [财务手册](s-payment-finance-handbook.md)。
> ⚠️ 各地执行细节与税率以办理时当地税务机关口径为准；本文是当前公开政策的通行做法，非税务师意见。

## 一、核心结论（三条）

1. **没有"系统对接"这回事。** 数电发票就是税务局的"电子税务局"（网页/APP）人工开票；微信支付与税务系统互不相通，中间没有 API 可接。微信只是收钱的 POS 机，发票是你在税务局系统里自己点出来的。
2. **系统侧已拍板口径就是最省力方案**：系统只做台账（invoices）+ 退款自动联动"待红冲" + 月度计税报表；人工只在三个动作进电子税务局——**开蓝票、冲红、季度申报**。
3. **工作量总账 ≈ 一年一个晚上。** 真正累人的不是日常税务，是办证那两周（一次性搬运）。

## 二、前置资质链（与办商户号是同一条线）

开票主体必须 = 收款主体：商户号是谁的名，发票就得以谁的名义开。

| 步骤 | 说明 |
| --- | --- |
| ① 个体户营业执照 | **Native 权限硬依赖**（评审 B7：无执照的小微商户开不了 Native 扫码）——办这张照一举两得：解锁收款，也解锁开票 |
| ② 税务登记 | 执照下来后电子税务局自动建户；去**确认税种核定 + 签三方扣款协议（银行代扣税款）+ 实名认证**。做完这步开票能力即解锁，**不需要税控盘**（数电时代已废除） |
| ③ 商户号 + Native 权限 | 原有办证清单不变（探索纪要 §12） |

不推荐自然人（个人）名义代开：电子税务局 APP 虽支持，但每笔都要走代开流程、按次预缴个税，长期经营不合适。

## 三、三件事的操作路径

### 3.1 开发票（蓝字发票）

电子税务局 → 开票业务 → **蓝字发票开具**。

- 抬头：个人客户写姓名即可；企业客户给名称 + 税号
- 品名：信息技术服务费 / 软件服务费
- 税率：小规模纳税人**月销 10 万（季 30 万）以下免增值税，开出来是"免税"普通发票**；超出部分按 1%（政策执行至 2027 年底）。你的量级大概率全程免税，**开票不产生税钱**

### 3.2 负值发票（红字发票 / 红冲）

不是"开一张负数票"那么随意，流程锚定原蓝票：

电子税务局 → 红字发票开具 → **选原蓝票 → 填红字确认单 → 开出负数红票**。

- 个人抬头普票、买方未做用途确认（未入账）的，**卖方可直接开，不需要对方确认**
- **选中原蓝票后抬头/金额/日期全部自动带出**——要"抄"的只有一个 20 位发票号
- 红开后申报表该期自动冲减销售额
- 与系统 invoices 状态机一一对应：`issued → pending_red_flush → red_flushed` + `red_invoice_no` / `red_confirmation_no` 回链退款单

### 3.3 申报（唯一躲不掉的固定义务）

**只要有商户号在收款，哪怕一张发票都不开，申报义务就存在**——这是办证的成本，不是开票的锅。

- 小规模纳税人**按季申报**增值税（季后 15 日内），免税额度内也要做免税申报，不能不报；很多省有一键申报（预填数据确认提交），10~20 分钟
- 经营所得按季预缴，次年 3 月底前年度汇算清缴
- **申报销售额 = 流水总额（含未开票收入）**，不只是开过票的——月度计税报表直接喂这个数（T1 口径：按全额，手续费不冲减）
- 忘记申报会被罚款——这比开票重要得多。嫌烦的明码标价解法：**代理记账，个体户行情两三千一年**全代办；建议第一年自己干一次再决定要不要花这个钱

## 四、"退税"不存在（别被这个词唬住）

- 免税额度内**一分钱增值税都不缴** → 不缴就没有"退"，预计月流水离 10 万差两个数量级，这一栏就是零
- 给**用户**退钱 = 微信退款 API，与税务局无关；税务侧只需红票把销售额冲平
- 向**税务局**退税只在"缴了税又红冲"时可能发生（大概率永不发生）；真发生了，红票在申报表自动冲减，多的结转下期或申请退还
- 手册"多缴退税三链材料"（原发票 + 红冲发票 + 退款单）是给万一的情况留档，**不是任务清单**

## 五、工作量账本

| 任务 | 真实频率 | 单次耗时 | 一年合计 |
| --- | --- | --- | --- |
| 开发票 | 用户主动索要才开；个人写作者无报销场景，估 0~10 张/年 | 10 分钟 | ~1 小时 |
| 红冲 | "开过票 × 又退款"交集，双重稀有 | 10 分钟 | 0~2 次 |
| 退税 | **不存在** | — | 0 |
| 申报 | 每季度一次（固定） | 10~20 分钟 | ~1.5 小时 |

## 六、系统侧：invoices 表就是"内部系统"

不需要新做系统，决策 #8 + §4 的 invoices 表就是全部。工作流与现行运维习惯一致（决策 #6：无 Web 管理页，MCP 直查 PG）。

**谁写什么：**

| 写入方 | 动作 |
| --- | --- |
| 系统自动 | 退款成功回调 → 该单已开票的行置 `pending_red_flush`（不用人发现，系统先标好） |
| 系统自动 | 未开票的订单退款 → 补一行 `superseded` 墓碑：此单已退款，永不许开票（防日后翻旧账要票的拒绝依据） |
| 人工 INSERT | 客户索票、税务平台开完蓝票后登记台账 |
| 人工 UPDATE | 冲红回来登记红票号 |

**SQL 习惯三段**（列名以立项 design 为准，此处示意）：

```sql
-- 登记蓝票（开完票后）
INSERT INTO invoices (invoice_no, order_no, 类型, 抬头信息, amount_fen, issued_at, status)
VALUES ('25317000...', '20260829xxx', '数电普票', '张三', 26500, '2026-08-29', 'issued');

-- 日常待办：月初扫一眼要冲红的
SELECT invoice_no, order_no, amount_fen, refund_no
FROM invoices WHERE status = 'pending_red_flush';

-- 冲红回来回登记
UPDATE invoices
SET status = 'red_flushed', red_invoice_no = '...', red_confirmation_no = '...'
WHERE invoice_no = '25317000...';
```

月度计税报表自带红冲明细（财务手册月报样例"开票/红冲 3 张/1 张"），**月报天然是提醒器，漏不了**。

## 七、什么时候才需要真正的 API 对接

日订单几十上百、用户要在产品里**自助申请并自动出票**时，才值得接第三方开票平台（百望 / 航信 / 诺诺等，包装电子税务局开放接口，收费）；税务局"乐企"直连要资质审批，面向大平台。**现在不预留**——invoices 表就是将来接 API 的落点，设计已兼容。

## 八、AI agent 能吸收哪部分、哪部分进不去

| 边界 | 内容 |
| --- | --- |
| ✅ 已自动化（payments 设计内） | 对账、月度计税报表、台账登记接口、退款自动联动"待红冲" |
| ✅ 能减轻 | 抬头收集：真有人要票时发个表单链接让客户自己填，照抄进税务平台 |
| ❌ 进不去 | 电子税务局的最终提交：实名认证 + 短信验证码/人脸的墙，agent 替不了也不该代登；但墙内就是"填表 → 点提交"，一年碰不了几次 |

## 九、对现有文档的影响

- **工程侧零新增**：决策 #8 与 invoices 表设计不改；本表工作流随 `s-wxpay-native` 立项进 design，不单独立项
- **办证清单增补两项**（探索纪要 §12）：执照下来后办税务登记 + 签三方扣款协议；电子税务局实名认证
- **invoices 已补字段**（2026-08-29）：`red_confirmation_no`（红字确认单号，与红票号是两个号码）+ 工作流一句话备注
