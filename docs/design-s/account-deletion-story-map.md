## 1. 主干（活动层）与步骤

```
〔A1 发现入口〕──〔A2 理解后果〕──〔A3 权益处置〕──〔A4 身份确认〕──〔A5 提交与撤销期〕──〔A6 执行与注销后〕
   找到入口         读后果清单       二选一处理权益     密码二次确认      15 天反悔窗口        去标识化 + 双端落场
   （唯一主路径）    作品/留存口径     （无则跳过）      错误可重试        提示可撤销/状态可查   会话失效/回登录页
```

**设计铁律（2026-08-29 用户裁定）：注销不允许"走不通"。** 自助是唯一主路径，且每类账号状态都保证有自助出口（忘记密码→登录页找回；有未消耗权益→退款或放弃二选一；撤销期→可撤销或等到期自动执行）——不存在"必须找客服才能注销"的设计场景。人工通道（R8）只是极端故障（页面异常等）的保险丝，正常用户永远到不了那条路径。

**用户**：S 端已注册用户（账号 = 用户名 + 密码，无邮箱无手机号——所以注销全程必须站内完成，任何"发邮件确认"的路径都不成立）。
**前置条件（2026-08-29 用户裁定）**：能到达注销页的用户**必然已登录**——注销功能不设计"未登录注销"路径。忘记密码的用户走登录页「忘记密码找回」恢复登录后，即可正常回到注销页自助办理；**忘记密码不属于注销功能的路径范围**，也不触发人工兜底（人工兜底只留给通道异常等自助确实走不通的情形）。
**核心场景差异**：有无未消耗套餐（待激活 / 排队中 / 消耗中）决定 A3 是否出现；是否反悔决定 A5 走撤销支线还是 A6 执行支线。

## 2. 故事卡

标记说明：〔MVP〕= 本次 change 实现；〔后续〕= 本次不做、需另立项；〔实施期〕= 功能同批的非设计任务（tasks 8.x）。

### A1 发现入口

**步骤**：打开 S 端控制台 → 进入「我的账户」设置区 → 找到注销入口

#### US-1.1 在账户设置里找到注销入口 〔MVP〕
> 作为已决定离开的注册用户，我想在控制台「我的账户」区看到明确的「注销账号」入口，以便不用写邮件等客服也能开始注销。

验收要点（→ R1）：
- [ ] 已登录用户进入控制台账号安全/账户设置区，可见「注销账号」入口，点击进入注销向导（原型态 `entry`）
- [ ] 入口位置符合账户设置信息架构：排在常规设置项（修改密码、我的设备、退出登录）之后、以警示色弱化呈现（安静不诱导）
- [ ] 入口、向导、确认、撤销全部站内完成；用户可见层不出现"请发邮件/等待邮件确认"作为主路径（账号无邮箱无手机号）

#### US-1.2 注销永可达：自助无死路，人工仅为法定保险 〔MVP〕
> 作为处于任何账号状态的用户（有套餐、想不起密码、撤销期中），我都有一条自助路能走完注销，永远不需要"求客服才能删号"；人工通道只是极端故障时的保险丝。

验收要点（→ R8；设计纪律卡，评审每张故事卡时对照）：
- [ ] 自助闭环覆盖全部账号状态：忘记密码→登录页「忘记密码找回」；有未消耗权益→退款或显式放弃**二选一必居其一**（放弃出口保证永不卡死）；撤销期→可撤销或等到期自动执行——任何状态都有自助出口，不存在"必须找客服才能注销"的设计场景
- [ ] 客服邮箱 alexee_zhu@163.com 仅作为极端故障（页面异常等）的保险出口保留于页脚（→ R8），不作为任何用户状态的主路径或预期路径出现
- [ ] 人工通道受理口径与协议 §三.4 兜底表述一致（15 个工作日口径随协议改版在实施期更新，见 tasks 8.1）

### A2 理解后果

**步骤**：打开注销向导 → 读后果清单（删什么 / 留什么 / 限什么）→ 确认已理解

#### US-2.1 后果清单完整且分组清晰 〔MVP〕
> 作为正在考虑注销的用户，我想在提交前一次看全"会失去什么、会保留什么、什么依法留存"，以便在知情的前提下做决定。

验收要点（→ R3 告知部分；R5 留存口径；R4 告知部分）：
- [ ] 向导第一步完整列出：账号凭据失效、**用户名永久封存（不再释放给任何注册）**、设备绑定全部解除、套餐功能终止
- [ ] 明示交易记录依法留存约 10 年、去除与身份的直接关联、不再日常展示（对应隐私政策第四章第 3 款、design P2 决策）
- [ ] 明示 15 天撤销期与"到期未撤销自动执行、无需再次确认"（原型态 `consequences`）
- [ ] 文案与《用户服务协议》§三.4、《隐私政策》口径逐条对得上；关键警示加粗；称呼用「你」、按钮全动词（design-language §13）

#### US-2.2 「本地作品不受影响」单独说清 〔MVP〕
> 作为 writers 最担心的用户，我想明确知道注销不会动我设备上的作品，以便放心走完流程。

验收要点（→ R6）：
- [ ] 后果清单"保留"分组的第一条：作品仅存于你的设备、本站没有副本、注销不读取不修改不删除任何作品数据（原型态 `consequences`）
- [ ] 后果清单同步给出**导出备份提示**（warn 语气，R6 新增 scenario）：建议注销前将小说文档导出并自行妥善保存——卸载应用、清理数据或更换设备可能导致作品无法找回，本站没有副本（2026-08-30 用户要求）
- [ ] 向导任何步骤不出现"删除你的作品/清理你的数据"这类会引起误解的表述
- [ ] C 端失效提示（US-6.1）与执行完成提示中重复该承诺，形成首尾呼应

### A3 权益处置

**步骤**：系统检查套餐台账 → 有未消耗权益：二选一 → 无未消耗权益：跳过直达

#### US-3.1 有未消耗权益时先处置、不受理注销 〔MVP〕
> 作为还有没用完套餐的用户，我想在注销前被明确要求处理这些权益（退款或放弃），以便我的钱不被悄悄清零。

验收要点（→ R2）：
- [ ] 存在待激活/排队中/消耗中权益时，向导展示权益清单（档位、状态、剩余/计划生效时间），提供且仅提供两个出口（原型态 `assets`）
- [ ] 未完成任一出口前，「继续注销」按钮不可用；即使前端绕过，服务端受理时按同一查询复验并拒绝受理（tasks 3.2）
- [ ] 「退款冻结」「已回收」状态权益不阻塞流程，不列入处置清单
- [ ] 无未消耗权益时整步跳过，向导从后果清单直达密码确认（原型态 `consequences` 注释标注）

#### US-3.2 出口一：去订单页退款 〔MVP〕
> 作为想拿回余额的用户，我想直接跳到既有退款流程按《退款政策》拿钱，以便不被引导成"白白放弃"。

验收要点（→ R2 + design D4；复用不新造）：
- [ ] 「去订单页退款」跳转既有订单详情退款流程（待激活全额退、消耗中按剩余秒数折算、原路退回微信、一般 1~7 个工作日到账——全部既有规则与文案，注销功能不发明任何资金规则）
- [ ] 点击后离开向导；退款完成后重新进入向导，权益复验自动通过（页面注释注明该往返）
- [ ] 明示在途退款不依赖账号存续：撤销期内申请退款、注销后到账均不受影响

#### US-3.3 出口二：显式放弃未消耗权益 〔MVP〕
> 作为不在乎余款的用户，我想勾选"放弃"直接继续注销，以便不被退款流程卡住。

验收要点（→ R2；design D4 / D2 第 4 步）：
- [ ] 放弃必须显式勾选确认句（"这些权益将作废，且不产生任何退款"），警示样式（warn 语气，原型态 `assets`）
- [ ] 放弃的权益在注销到期执行时置为已回收、不再可用、不产生退款；放弃动作写入审计（trade_events），可追溯事后争议
- [ ] 撤销注销则放弃不生效、权益原样保留（放弃只在注销执行时兑现——随 US-5.3 恢复语义）

### A4 身份确认

**步骤**：汇总确认信息 → 输入密码 → 提交

#### US-4.1 密码二次确认后提交 〔MVP〕
> 作为即将提交注销的用户，我想用密码证明"这是我本人"，以便他人无法拿我登录态恶意注销我的账号。

验收要点（→ R3）：
- [ ] 提交前展示摘要（账号、权益处置结果、撤销期截止日、到期执行日）+ 密码输入框；密码校验通过才受理（原型态 `password`）
- [ ] 页面说明密码仅用于本次确认；本站不会通过邮件/短信联系用户（没有该触达渠道）
- [ ] 撤销操作采用同一密码确认强度（→ R4，design D3）

#### US-4.2 密码错误被拒且可重试 〔MVP〕
> 作为输错密码的用户，我想立刻知道"没提交成功"，以便放心重试而不是担心已被注销。

验收要点（→ R3 scenario 密码错误拒绝提交）：
- [ ] 密码错误时明确提示"密码不正确，注销申请未提交"，并提供重试出口（原型态 `password-err`）；想不起密码的用户走登录页「忘记密码找回」，恢复后重新进入向导（→ US-1.2 裁定）
- [ ] 错误状态下账号状态无任何变化（未进入撤销期）

### A5 提交与撤销期

**步骤**：提交成功 → （支线 a）撤销期内反悔 → 密码验证 → 撤销恢复 ∕（支线 b）到期不撤销 → 自动执行

#### US-5.1 提交成功页讲清"接下来会发生什么" 〔MVP〕
> 作为刚提交申请的用户，我想知道截止日期、到期会自动执行什么、现在还能不能反悔，以便掌控自己的账号。

验收要点（→ R4；R7）：
- [ ] 受理确认页展示：申请已提交、撤销期 15 天、到期自动执行的具体日期、撤销期内付费与套餐功能暂停（原型态 `submitted`）
- [ ] 到期执行的处置范围预告：凭据失效、设备解绑、按选择处置权益、交易记录依法留存、客户端回登录页、本地作品不受影响
- [ ] 主操作为「撤销注销」；页脚保留人工兜底邮箱

#### US-5.2 撤销期内登录即见状态、功能受限 〔MVP〕
> 作为处于撤销期的用户，我想一登录就看到"账号正在注销中、还剩几天、怎么撤销"，以便不会误以为账号被盗。

验收要点（→ R4 scenario 撤销期内登录提示可撤销；R7；R4 付费受限）：
- [ ] 撤销期账号认证被拒于正常登录，界面返回结构化状态：已申请注销 + 剩余天数 + 「撤销注销」按钮（原型态 `suspended`，warn 提示条）
- [ ] 撤销期内账号无法使用付费与套餐功能（套餐卡置为"已申请注销 · 暂停使用"），仅撤销动作可用
- [ ] 状态数据来自统一的状态查询能力（是否已申请注销 / 剩余天数 / 到期执行日期，供 S 端界面与 C 端消费）（→ R7）

#### US-5.3 撤销即恢复，过期自动执行 〔MVP〕
> 作为反悔了的用户，我想验证密码后一键撤销、账号立即恢复原状，以便损失为零地留下来。

验收要点（→ R4 scenarios 撤销成功账号恢复 / 到期自动执行）：
- [ ] 撤销需密码验证 + 确认弹层（原型态 `revoke-confirm`）；成功后账号立即恢复正常、申请作废、套餐与设备按原状态继续（原型态 `restored`）
- [ ] 撤销后如再次申请注销，撤销期重新计算
- [ ] 到期未撤销：系统自动执行全部处置，不再向用户要第二次确认（界面已在 US-5.1 预告）
- [ ] 与到期执行的竞态由服务端保证（撤销成功则执行必然失败、反之亦然——实现侧 CAS，tasks 3.3/3.4）

### A6 执行与注销后

**步骤**：到期执行 → C 端下次请求失效回登录页 → 该账号永不可再登录 → 数据进入留存态

#### US-6.1 C 端凭据失效、回到登录页、作品原地不动 〔MVP〕
> 作为账号已被注销的桌面客户端用户，我想客户端干净地回到登录页并明确告诉我作品还在，以便不慌、能立刻改用新账号。

验收要点（→ FH1；R6）：
- [ ] 注销执行后，客户端持有 JWT 在下次请求被拒，代理层清空 config.json 中的 token 与用户名并导航回登录页；不循环请求、不吞掉当前操作上下文
- [ ] 登录页失效提示包含"你设备上的作品仍完好保留"（原型态 `after` 的 C 端示意，复用既有登录屏、无像素变化）
- [ ] 失效后重新以有效账号登录即可正常进入工作台；全程不触碰本地 SQLite 作品数据（tasks 5.1/5.2 断言）

#### US-6.2 已注销账号的一切认证被拒、口径清晰 〔MVP〕
> 作为试图用旧账号登录的用户，我想得到明确的"账号已注销"结果与出路（注册新号 / 找客服），以便不反复尝试。

验收要点（→ R5 scenario 注销后认证被拒绝；R8；design D5）：
- [ ] 原用户名 + 密码（哈希已置空）及一切旧凭据均无法通过认证；界面提示账号已注销（原型态 `after` 的 S 端示意）
- [ ] 出口：注册新账号（原用户名已永久封存、提示不可用）或联系客服 alexee_zhu@163.com
- [ ] 注销账号的订单/交易信息不再出现在任何日常界面；交易记录依法留存约 10 年（去标识化，仅争议举证等法定用途）

| P5 保险丝（正常用户到不了） | 仅页面异常等极端故障 → 客服邮箱人工办理；自助闭环（见 US-1.2）保证正常状态永远到不了这条路径 | US-1.2 / 4.2 |
| P6 执行之后 | 到期执行 → C 端回登录页 → 原凭据永拒 → 新号或人工 | US-6.1 / 6.2 |

## 4. 范围标记

- **MVP 线（本次 change 全量实现）**：US-1.1 ~ US-6.2 全部故事。本次无"分期上线"的拆分——注销权是法定义务，砍掉任何一段（如不告知留存、不设撤销期）都会破坏合规闭环。
- **后续迭代（本次不做，需另立项）**：
  - C 端客户端内直达注销入口（本次仅 S 端网页，C 端只做失效回登录页）；
  - 注销原因收集与挽留策略（涉及个人信息最小必要原则与体验争议，暂缓）；
  - 人工兜底工单化（邮箱 → 工单系统，含时效统计）。
- **实施期同批（非设计任务，tasks 8.x）**：《用户服务协议》已于 2026-08-29 先行写入完整注销条款组（**§三.4–7**：自助入口 + 客服兜底双通道、15 天撤销期与到期自动执行、六项后果告知、效力存续），《隐私政策》口径已同步——实施期仅做逐条核对（tasks 8.1–8.3），不存在"协议仍写人工 15 个工作日"的窗口期。

## 6. 待拍板差异（设计侧发现的、spec 未定或跨工件不一致项）

1. **「去退款」离开向导后的往返语义**（US-3.2）：spec 只要求"提供去退款出口"，未定义离开向导后是否自动回来。本设计取：离开向导 → 用户自行完成退款 → 重新进入向导，权益复验自动通过（向导不驻留后台等待、不做跨页状态保持）。理由：无多表事务环境与幂等复验（design D4）天然支持"每次进向导都重查"，做自动回跳反而引入跨页状态。若业务方期望"退款完成自动回向导"，需另立通知机制，成本不成比例。
2. **放弃勾选与撤销的语义边界**（US-3.3）：spec 说"放弃的权益随注销执行作废"，未明说撤销后权益如何。本设计取：放弃仅在注销**执行时**兑现，撤销期内撤销则权益原样保留。理由：与"到期自动执行才处置"的状态机一致（design D2 第 4 步只在执行序列中），也避免"勾了放弃又撤销、权益已没了"的争议。建议在 tasks 3.4 验收中断言该语义。
3. **提交成功页/撤销期提示条的语气档位**：proposal 状态语言只定了"撤销期中 = pill-status warn、执行完成 = ok"，未定"提交成功"瞬间态。本设计取 warn（钟形图标 + "已受理"而非"成功"），理由：受理的语义是"倒计时开始"而非"恭喜完成"，ok 的庆祝感与场景相悖。与 proposal 词汇零新增。
4. **既有原型退款到账文案不一致（跨工件观察，非本功能缺陷）**：`prototypes/refund.html` 与 `console.html` 写"一般数分钟至 3 个工作日到账"，而法律定稿《退款政策》§四.3 与 design D4 均为"**1~7 个工作日**"。本功能原型一律采用 1~7 个工作日口径；建议支付侧原型在下次登记簿修订时同步改正，避免两处界面承诺不同。

**已裁定（不再开放）**：

- **注销永可达（2026-08-29 用户裁定）**：自助注销设计上**不允许"走不通"**——每类账号状态都有自助出口（找回密码/退款/放弃/撤销/等到期），人工通道（R8）降为极端故障保险丝，不作为任何用户状态的预期路径。US-1.2 重写为设计纪律卡，P5 更名为"保险丝"，§1 主干与角色说明同步。
- **忘记密码路径（2026-08-29 用户裁定）**：能到注销页必然已登录；忘记密码走登录页「忘记密码找回」恢复后回向导自助办理，**不属于人工兜底受理范围**（R8 只留通道异常等自助故障）。US-1.2 / US-4.2 / P5 / §1 前置条件与原型 `password-err` 态均已按此更新，登记见 `prototypes/ADJUSTMENTS.md`。
