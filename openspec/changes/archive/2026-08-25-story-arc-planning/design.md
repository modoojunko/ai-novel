# 设计：主线拆纲（story-arc-planning）

## Context

- C端 后端是 FastAPI + SQLAlchemy/SQLite，数据已全量入表（#159-#163 迁移后），main.py lifespan 里做幂等 DDL 升级存量库。
- 设定项已有「整存整取」范式：简介、伏笔等都是一个 key 存一份内容，走 `GET/PUT /api/novels/{id}/story` 一族端点。
- AI 能力已有统一范式（settings/ai_router.py）：`require_ai_access` 会员门控 → 读提示词模板 → 调 chat → 剥壳 `json.loads` → `record_usage` 计量。
- 前端设定页是卡片式（OgPane 等），表单组件与 Modal/toast 均有现成封装（换装 v2 终态写法：btn/seg/Modal/color-mix/oklch）。

## Goals / Non-Goals

**Goals:**
- 主线卡作为普通设定项落地：免费可见可填，存取走既有设定项范式。
- AI 四步向导复用既有 AI 端点范式与会员拦截口径，提示词模板化。
- 存量书零迁移成本：无主线数据 = 空表单。

**Non-Goals:**
- 不做主线下游消费（AI 卷纲、提示词注入）——后续 change。
- 不改卷纲/章纲现有流程；分卷表只是「规划草稿」，不与 volumes 表联动。
- 不做向导的多轮自由聊天：每步固定「一次 AI 调用 + 作者确认/修改」。

## Decisions

### D1 主线存法：一个设定项 key，整存整取
主线是设定不是账本（用户已拍板）：一张卡一个 key，内容为一份 JSON（一句话 + 结局三字段 + 分卷行数组），读写整份覆盖，与简介/伏笔同族。
- 备选：把分卷拆成关系表（volumes 规划表）。否决——规划期行数不定、频繁整版重写、且不与正式 volumes 表联动，关系表只增加复杂度。

### D2 向导状态：以卡片数据为准，不建独立会话表
四步产出每步落卡（草稿写进主线 JSON，可带 `wizard_step` 标记当前进度）；中途退出再进，按卡片上已有内容推断从第几步续。
- 备选：独立向导会话表（存对话历史）。否决——「可续」只需要知道走到了第几步和已产出的内容，这些都在卡片上；避免引入会话生命周期管理。
- 对话中的临时输入（作者的原话、纠正）不持久化，丢了就重说——向导是工具不是聊天记录。

### D3 AI 端点：四个小端点，各配一个提示词模板
`POST /api/novels/{id}/story/arc/wizard/{step}`（step ∈ condense | ending | split | audit），全部走 `require_ai_access`。每个端点入参简单（作者输入 + 卡片当前内容），出参结构化 JSON（剥壳范式），前端按步渲染。
- 备选：一个端点带 step 参数 + 一个大提示词。实际上等价，但四个模板分开写各自更聚焦、可独立调优；端点仍收在同一 router。

### D4 前端：主线卡 = 普通表单卡；向导 = 卡内分步面板（非 Modal 长对话）
主线卡三块表单（一句话输入、结局三字段、分卷行编辑器——行增删、卷名/冲突/章数、一键「待定」）。「AI 帮我拆」点开在卡内展开分步面板，逐步替换卡片内容为草稿态；免费用户点击走既有全局会员拦截弹窗。
- 每步 AI 产出填入表单后即为普通可编辑内容，不区分「AI 写的/人写的」。

### D5 就绪项：设定清单加「主线」
READINESS_CHECKERS 按既有模式加一项：主线 JSON 有有效内容（至少一句话或一行非待定分卷）即算完成；空 = 软提醒，不拦任何流程。

## Risks / Trade-offs

- [主线 JSON 被手改后 `wizard_step` 失真 → 续步判断错位] → 续步只做「从第一个未完成步骤开始」的保守推断，宁可选早不选晚；作者可直接跳步（步骤条可点）。
- [AI 返回的 JSON 剥壳失败（模型不听话）] → 沿用既有剥壳+重试范式；失败 toast 报错，作者手填不受影响。
- [四步每步一次 AI 调用，成本敏感] → 每步调用即 `record_usage` 计量，与其他 AI 功能口径一致；不另做限流。
- [分卷表与正式 volumes 表口径混淆（规划 ≠ 实际卷）] → UI 文案明确「分卷规划」，本 change 不做任何同步/联动。
